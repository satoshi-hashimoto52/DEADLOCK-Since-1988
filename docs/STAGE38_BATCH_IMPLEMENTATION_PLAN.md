- オンラインの一人称の武器の表示を、オフラインの `WeaponViewModel`・`PixelWeaponArt` と共通にします。

- 武器の状態は、サーバーが確定した値に従います。
- 射撃・命中・弾薬・ダメージの権威は、サーバーに残します（D-071 を変えない）。

## 3. オンラインの武器の表示を共通にする計画（1-2）

### 3-1. 今の違い（2026-11-05 にコードを読んで確認）

| 項目 | オフライン（`WeaponViewModel`） | オンライン（`OnlineGameView`・`OnlineSpectatorView`） |
|---|---|---|
| 描き方 | 視点用カメラ（縦の視野50°、z＝1）の SpriteRenderer | UI の Image（860×640 の枠、縦横比を保つ） |
| 腰だめの位置・大きさ | 配置プロファイル（右下に合わせる、画面の比で動く、`HipShift*`）。画面の高さの約90% | 右下から60だけ内側に置く固定の配置。高さは約45% |
| ADS | 照星の先端が画面の中央 | 下端の中央に合わせるだけ。照星は中央に来ない |
| 反動・リロード・持ち替え・揺れ | あり | なし（画像を切り替えるだけ） |

### 3-2. 作り方（案）

1. **見た目の計算を、共通の部品として切り出します。**
   - `WeaponViewModel.LateUpdate` の位置・回転・大きさ・クロスフェードの計算です。
   - 入力：プロファイル、画面の比、ADS の度合い、反動の量、リロードの進み、持ち替えの度合い、移動の速さ。
   - オフラインは、今と同じ結果になるようにします（回帰テストで確かめる）。
2. **オンライン用の入力の元を作ります。** 入力は、サーバーが確定した `ArsenalNetState` です。
   - 持ち替え：`Current`・`Switching`
   - リロード：`Reloading`
     - 進み具合は送られていません。今の値（リロード中かどうか、`GunSpec.ReloadTime`）から、見た目だけを計算します。
     - 足りない場合は、状態に開始の時刻を足す案があります（通信の形の変更。実装のときに判断）。
   - 反動：`ShotsFired` が増えたときです。
   - ADS：今と同じ、手元の入力（`router`）の値です。表示だけに使い、権威はサーバーのままです。
3. **オンラインの一人称と観戦の表示を、UI の Image から視点用カメラと SpriteRenderer に置き換えます。**
   - 同じ `WeaponViewProfile`・画像・色替えを使います。
   - ナイフは `MeleeViewModel` と同じように扱います（範囲は実装のときに確かめる）。
4. **サーバー側のコードは変えません**（射撃・命中・弾薬・ダメージ）。

- **気をつけること：** 反動を確定した `ShotsFired` で出すと、往復の時間だけ遅れて見えます。手元で先に反動を出す（予測する）方法は、「サーバーの確定値に従う」という決定と食い違うので、使う場合はユーザーの判断が要ります。
- **要調査：** オンラインの銃口炎と弾の線の出し方を調べ、オフラインの `TryGetMuzzleScreenPoint` と合わせられるか確かめます。
- **影響を受けるテスト：** `OnlineSpectatorViewTests`（一人称の画像と仮表示）、`WeaponView` の文字列（`image:hip` など）を使うテストやツール。

## 4. AssetPipeline の計画（1-3）

### 4-1. 統合ブランチ用の登録先（側面図の登録の前に行う）

- `config/pipeline.json` の `repositories` に、新しい登録先（名前の案：`weapons_integration`）を足します。
  - branch：feature/integration-smg-dungeon
  - worktree：統合ブランチの作業ツリー（相対パス）
  - remote・allowed_roots・exclude は、今の `weapons` と同じ考え方にします。
- 今の `weapons`（weaponlab）と、その素材 `weapon.smg.side` は、変えません。

### 4-2. あいまいさをなくす

- **新しい武器の素材：** assets.json の素材ごとに、登録先（`repository`）を明示します。
- **明示がない場合：** 区分の登録先や既定の登録先へ自動で回さず、**エラー**にします（武器の区分）。
  - 今の `repository_for` は、明示がないと既定の登録先へ戻ります（config.py:98）。武器の区分では、この戻り方を禁止します。
- **確認すること（実装のとき）：** assets.json で、素材ごとに `repository` を書けるかどうか。

### 4-3. 誤登録を防ぐ検査（必須）

- 今あるもの（registry.py:173 `check_repo`）：
  - 作業ツリーの最上位であること
  - 今のブランチが設定と同じであること（自動では切り替えない）
- **足すもの：**
  1. 作業ツリーのパスが、設定の `worktree` と同じであること（シンボリックリンクを解いてから比べる）。
  2. remote の URL が、設定の remote と同じリポジトリを指していること。
  3. 登録先のパスが、その登録先の `allowed_roots` の中にあること。
  4. 同じ素材ID が、別の登録先にすでに登録されていないこと。
  5. 登録の計画（dry-run）に、登録先の名前・ブランチ・作業ツリーを表示し、実行のときに登録先の名前を明示させること。
  6. 外れた場合は止めて、何もしないこと。
- テストを足します（ブランチ違い・作業ツリー違い・remote 違い・明示なし・二重登録）。
  - test_weapon_side.py:55 は、weaponlab のブランチを確かめています。このテストは残し、新しい登録先のテストを別に足します。

### 4-4. 腰だめ・ADS の区分（全素材がそろってから）

- `weapon_fp_hip`・`weapon_fp_ads` を足します（判定の案は Stage 38 仕様書 7-2）。
- 今の判定（寸法・形式・内容・透明な画素）は、流用します。
- `transparent_edges` は4辺すべてを見るので、使いません。代わりに、次の判定を新しく作ります。
  - 辺ごとの透明
  - 空ける場所
  - 4×4 の格子
  - ADS の照星の位置
  - アルファ2値の strict 判定
- 最初は、外れたらユーザーの確認に回します（NEEDS_REVIEW）。規格を確定した後で strict にします。
