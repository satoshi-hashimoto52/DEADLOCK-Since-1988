# AssetPipeline の永続管理の方針（第26段階、2026-10-30）

AssetPipeline（`DEADLOCK/AssetPipeline/`）は、今は Git の管理外にあり、1台の Mac にしかない。
素材の受付・検査・承認・登録、武器側面画像の共通規格、登録先の振り分け、`_inbox` の整理、`commit-plan`、`push --record-only`、登録履歴、pytest（115件）が、すべてこの Mac の中にある。
この文書は、その管理方法を比べて推奨案を示す。**今回は、リポジトリの作成も大量のコピーもしていない。**

## 2. 管理方法の比較

| 項目 | 案A：独立した非公開リポジトリ | 案B：DEADLOCK 用の非公開ツールリポジトリ | 案C：ゲームのリポジトリ（公開）にソースだけ |
|---|---|---|---|
| 安全性 | 高い（非公開。運用データを分けて扱える） | 高い（同じ） | **低い**。公開リポジトリなので、設定の絶対パス、元のファイル名、素材の識別子を毎回選り分ける必要がある。間違えると公開される |
| 保守性 | ソースの履歴を管理できる。ただし、DEADLOCK 専用の設定（素材 ID、登録先）の置き場所に迷う | ソースと DEADLOCK 専用の設定と仕様書を、1か所で一緒に管理できる | ゲームと同じ場所で見られるが、ゲームのコミット単位と混ざる |
| 復旧のしやすさ | clone と運用データの復元で戻せる | 同じ | ソースは戻せるが、運用データは別に必要 |
| チーム開発 | 権限を分けられる | 権限を分けられる（ゲームの公開リポジトリとは別） | ゲームと同じ権限になる |
| 複数の PC への移行 | clone と、機械ごとの設定ファイル | 同じ | 同じ |
| バックアップ | GitHub（非公開）と、運用データのスナップショット | 同じ | ソースは公開の GitHub。運用データは別 |
| 管理の手間 | リポジトリが1つ増える。設定をどこに置くか決める必要がある | リポジトリが1つ増える | 少ないが、コミットのたびに公開してよいかの選別が必要 |
| 将来の再利用 | 高い | 中程度（後で汎用の部分だけを別のリポジトリに切り出せる） | 低い |

### 推奨：案B（DEADLOCK 用の非公開ツールリポジトリ）

- 今の AssetPipeline は、設定（素材 ID、登録先、共通規格）、仕様書との対応、テストの前提が DEADLOCK 専用。ソースだけを汎用化しても、すぐに使い回せるわけではない。案Bなら、設定と仕様を一緒に管理できる。
- 公開リポジトリとは別にするので、絶対パスや素材の識別子が公開される危険がない（案Cの欠点を避けられる）。
- 開発者が1人なので、リポジトリは1つで足りる。ほかのプロジェクトで使うことになったら、汎用の部分（`scripts/`・`tests/`）を、そのときに案Aの形で切り出せる。
- **注意：** 非公開リポジトリにも、運用データ（原本画像、状態、履歴）は入れない。ソースと運用データは、バックアップの方法を分ける（3章）。

## 3. 永続管理とバックアップの設計

### 3-1. ソース（案Bのリポジトリ）

- 入れるもの：`scripts/`、`tests/`、`README.md`、`pytest.ini`、`requirements.txt`、`assetpipe`、`config/assets.json`、`config/pipeline.example.json`、文書（この方針、運用ルール）。
- 入れないもの：`config/pipeline.json` の機械ごとの値、`_inbox/`、`processing/`、`candidates/`、`approved/`、`rejected/`、`archive/`、`reports/`、`.venv/`、キャッシュ、禁止語のリスト。
- 機械ごとの値の分け方（今後の実装）：
  - `pipeline.json` を、共通部分と、機械ごとのファイル（例：`config/pipeline.local.json`。`.gitignore` で除外する）に分ける。
  - 作業ツリーの場所は、機械ごとのファイルか環境変数で指定する。
- 変更は、ブランチで行い、pytest に合格してからコミットする。リリースするときはタグを付ける（例：`assetpipe-2026.10.30`）。

### 3-2. 運用データ（スナップショットと SHA-256）

- 対象：
  - `candidates/`、`approved/`、`rejected/`、`archive/`
  - `reports/pipeline_state.json`、`history.jsonl`、`receipts/`、`inbox_audits/`、`logs/`
  - `reports/<作業名>/`
- 方法：
  - 監視を止めた状態で、作業ごとのフォルダにコピーする（例：`_device_backup/<日付>_assetpipe_data/`）。
  - `SHA256SUMS.txt` と `MANIFEST.json` を付ける。
  - `MANIFEST.json` には、AssetPipeline のソースのコミット（案Bのリポジトリ）、受付の件数と状態ごとの件数、REGISTERED の素材 ID・登録先・SHA-256 の一覧、各登録先のリポジトリの HEAD を書く。
  - 元のデータは移動も削除もしない。
- 周期：
  - **作業単位が終わるたび**（承認・登録・`_inbox` の整理の後）：状態・履歴・原本画像（小さいので毎回）。
  - **週に1回**：`reports/<作業名>/` を含む全体。
  - **月に1回と、大きな変更の前**：外部のディスクか、暗号化したクラウドへ、もう1部コピーする（公開の場所には置かない）。
- 保存先：
  - Mac の中（`_device_backup/`）と、外部の場所の2か所。
  - どちらも、ゲームの公開リポジトリと、案Bのリポジトリの外。

### 3-3. 復旧と、復旧テスト

1. 案Bのリポジトリを clone し、`.venv` を作り直す（README の3〜4章）。
2. 運用データのスナップショットを、同じ構成に戻す。`shasum -a 256 -c SHA256SUMS.txt` で照合する。
3. 機械ごとの設定（作業ツリーの場所）を指定する。
4. 確認（どれも読み取りのみ）：
   - `./assetpipe status`
   - REGISTERED の全件の `verify`（登録先の SHA-256、Git の状態、`.meta` の GUID）
   - `commit-plan`（単位として登録した素材）
   - `inbox`
5. pytest を全件実行する。
6. **復旧テストは、3か月に1回と、AssetPipeline の大きな変更の後に行う。** 一時的なフォルダ（`ASSETPIPE_ROOT` で指定する）に戻して、上の確認をすべて行う。本来のデータには触れない。

- 途中の受付（候補・承認済み・配置済み）も、状態と原本画像がスナップショットにあるので、そのまま戻せる。
- 素材 ID と Unity の画像の対応は、`config/assets.json`（素材 ID と登録先）、状態の記録（SHA-256、コミット）、`MANIFEST.json` で保たれる。
- 注意：状態の記録には、登録先の作業ツリーの絶対パスが入っている。別の PC で場所が違う場合、`verify` は今のままでは失敗する。複数の PC で使う前に、記録のパスを読み替える仕組み（例：作業ツリーの名前で対応づける）を作る必要がある（未実装）。

### 3-4. 運用ルールを続けること

- `_inbox` は受け渡し専用で、作業単位の終わりに整理する（AssetPipeline の README 15章。`inbox --prune-empty` を含む）。
- 単位として登録する素材は、`commit-plan` で確認してから、まとめてコミットする（16章）。push 済みの記録は `push --record-only` で合わせる（17章）。
- 公開リポジトリには、AssetPipeline の運用データを入れない（`docs/COMMIT_SAFETY.md`）。

## 4. 次に行うこと（ユーザーの判断が必要）

1. 案Bを採用するかどうか。採用する場合は、非公開リポジトリの名前と場所。
2. `pipeline.json` を、共通部分と機械ごとの部分に分ける実装。
3. 運用データのスナップショットを、初めて取得すること（約0.9 GB。今回は取得していない）。外部の保存先を決めること。
4. 状態の記録にある絶対パスを、別の PC で読み替える仕組み（複数の PC で使う場合）。
5. 最初の復旧テスト。
