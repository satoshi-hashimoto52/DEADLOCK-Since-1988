# iPhone アプリデータ誤削除事故（2026-10-28）— 公開用の概要

この文書は公開リポジトリ用の要約です。端末の識別情報、実際の設定値、アプリ内のファイル一覧、Mac 上の保存場所、ログの原本は含めません。
それらの詳細記録は、開発者の Mac 上（リポジトリの外）にだけ保存しています（[§8](#8-記録の扱い公開用とローカル専用)）。

復旧機能の仕様と手順：[`IOS_DATA_RECOVERY_PROCEDURE.md`](IOS_DATA_RECOVERY_PROCEDURE.md)

## 1. 概要

| 項目 | 内容 |
|---|---|
| 日時 | 2026-10-28 10:17 JST |
| 対象 | 開発用の iPhone に入れた開発ビルドのアプリ（DEADLOCK 0.1.0） |
| 操作 | Xcode の `devicectl` で、アプリのデータ領域へフォルダをコピーした。その際、既存の内容を削除するオプション（`--remove-existing-content`）を付けた |
| 意図 | 新しく作った試験用フォルダの中だけで、このオプションの影響範囲を確かめること |
| 結果 | アプリのデータ領域のほぼ全体が削除された（291項目のうち286項目） |

## 2. 原因

- 影響範囲を確かめていない削除オプションを、本物のアプリのデータに対して実行した。
- 試験を、試験専用の領域や試験専用のアプリに隔離していなかった。

## 3. 影響

| 区分 | 件数 | 内容 | 対応 |
|---|---|---|---|
| A 復元が必要 | 3 | 武器調整の保存値（JSON 2件）、設定（PlayerPrefs の実体 1件） | 復旧した（§5） |
| B Mac で保管 | 246 | 開発用の検証画像・自動撮影・検証ログ | 事故の直前に Mac へ取り出してあった。iPhone には戻さない |
| C 復元不要 | 10 | OS のキャッシュと自動生成ファイル | 起動時に作り直される |

- 事故の直前に、データ領域を Mac へ2回、独立に取り出していた。バックアップのある 254件は、2回分と一覧の SHA-256 がすべて一致した。
- 設定ファイル（PlayerPrefs の実体）にはバックアップがなかった。値は、過去の実機検証ログに記録された確定値だけから、項目ごとに再構成した。推定値は使っていない。

## 4. 再発防止策

### 4-1. 実機データの操作

1. 実機のアプリのデータの削除と置き換えは、原則として禁止する。必要なときは、対象を一覧にし、ユーザーが明示的に承認してから行う。
2. `--remove-existing-content`、アプリのアンインストール、データ領域の置き換えは使わない。
3. 端末へ書き込む前に、データ領域全体をバックアップし、SHA-256 を照合する。照合が済むまで書き込まない。
4. 初めて使うコマンドやオプションは、本物のアプリのデータで試さない。試験専用の領域か、試験専用のアプリで確かめる。
5. 実行の前後で一覧を比べる。対象の外に変化があれば、すぐに中止して報告する。
6. 検証の出力（キャッシュ）と、ユーザーの設定・保存データは分けて扱う。検証は設定を書き換えない。

### 4-2. 検証画像の容量管理

- 装備画面の自動撮影は、標準では無効にした。起動時に指定したときだけ撮影する。
- 開発用の画像とログの保存先を `Library/Caches/DeadlockDevCaptures/` にまとめた（`DevCaptureStore`）。
  - アプリは何も消さず、上書きもしない。
  - 上限（ファイル数・容量）を超えるときは、古いものを消すのではなく、書き込みを止める。
- 古い出力の片付けは、Mac に取り出して照合した後で、人が判断して行う。

## 5. 復旧の技術的な概要

- 端末へファイルを直接コピーする方式は使わなかった。iOS の設定は OS のプロセスが別に保持しているため、設定ファイルを置き換えても効く保証がない。
- 代わりに、**開発ビルドだけに入る復旧機能**（`DeviceDataRecovery`、アセンブリ `Deadlock.Dev`）を作った。アプリ自身が、`PlayerPrefs` と武器調整の保存処理で書き戻す。
  - 起動時の環境変数で、`dry-run` か `apply` を明示したときだけ動く。
  - 対象は許可リストの項目だけ（設定8キー、JSON 2件）。
  - 書く前にすべてを検査する（許可リスト、値、SHA-256、JSON の形式）。一つでも合わなければ、何も書かない。
  - 既にある値は上書きしない。二重に実行しても結果は変わらない。
  - 結果は、キー・ファイル単位で記録する。
- 復旧データは、Mac のバックアップを照合して生成した。リポジトリには入れない（`Assets/Game/Verification/`、Git の対象外）。
- Release ビルドには、復旧のコードもデータも入らない。

## 6. 検証方法と結果

- **Editor（Mac、batchmode）：**
  - 設定は辞書、ファイルは一時フォルダに書く隔離環境で、復旧処理を検証した。実際の PlayerPrefs は読むだけで、テストの前後で値が変わらないことを確認した。
  - iOS 向けに、スクリプトを Release と開発ビルドの2通りでコンパイルした。Release の出力に、復旧のコード・データ・関連の文字列がないことを確認した（`ReleaseBuildExclusionTests`）。
- **実機：**
  - 2026-10-29 に、上書きインストールした開発ビルドで、先に dry-run、次に apply を実行した。
  - apply の結果は `ok`。読み戻しで、設定は値の一致、JSON は SHA-256 の一致を確かめた。
  - その後の dry-run では、すべての項目が `already-restored` になった。
  - 以後の実機検証では、毎回インストールと確認の前後で、復旧したデータが変わっていないことを照合している。
- **自動テスト：** EditMode・PlayMode の全件に合格（件数は `docs/PROGRESS.md` の各段階を参照）。

## 7. データ保護の運用ルール

- 実機へのインストールは上書きだけにする。アンインストール、データ領域の削除・置き換え、端末へのファイルコピーはしない。
- 検証は PlayerPrefs を書き換えない。
- 設定と保存値は、インストールの前後と確認の後で照合する。端末がロックされている場合や異常があれば、止めて確認する。
- バックアップの原本は変更しない。作業ごとに新しいフォルダを作り、`SHA256SUMS.txt` を付ける。
