# コミット前の安全確認（公開リポジトリ）

このリポジトリは公開されている。コミットしたものは、取り消しても履歴に残り、複製されることがある。
コミットする前に、この文書の確認をすべて行う。

## 1. 公開してよいもの・ローカル専用のもの

| 区分 | 例 | 置き場所 | Git |
|---|---|---|---|
| 公開用 | 仕様、設計、実装、テスト、障害の概要・原因・再発防止策、手順の技術的な概要、テスト結果 | リポジトリ | 管理対象 |
| ローカル専用 | 端末の識別子（UDID・devicectl の ID など）、アプリのデータ領域のファイル一覧、PlayerPrefs や保存データの実データ、復旧データ、端末のログ、SHA-256 付きの検証記録、Mac 上の絶対パス、メールアドレスなどの個人情報 | リポジトリの外（`../_device_backup/` の作業ごとのフォルダ） | **入れない** |
| 開発用の検証コード | 実機での確認スクリプト、生成した復旧データ | `Assets/Game/Verification/` | **入れない**（`.gitignore`） |

- ローカル専用の記録は、原則としてリポジトリの外に置く。
- やむを得ずリポジトリの中に置くときは、名前を `*.local.*` にするか、`local/` フォルダに入れる。どちらも `.gitignore` で除外している。
- 公開用の文書は、ローカル専用の記録の派生版として作る（原本は変更しない）。識別情報は書かずに、「開発用の iPhone」のように一般的に書く。
- Team ID と Bundle ID は、ビルド設定（`ProjectSettings.asset`、`IOSPlayerSetup.cs`、`Tools/ios-device-run.sh`）に必要なので、そこでは変えない。
  - 以前のコミットから、すでに公開されている。
  - 文書には Team ID を書かない（2026-10-30 に既存の文書から伏せた）。
- 文書でファイルを指すときは、リポジトリのルートからの相対パスで書く。Mac の絶対パスは書かない。リポジトリの外のものは `<Mac のダウンロードフォルダ>` のように書く。

## 2. `.gitignore` だけでは守れないもの

- `.gitignore` は、まだ追跡していないファイルにしか効かない。追跡済みのファイルは、ignore に書いてもコミットに入る。
- 追跡済みかどうかは、`git ls-files -- <パス>` で確かめる。
- `git ls-files -ci --exclude-standard` を実行して、何も出ないこと（ignore に該当する追跡済みのファイルがないこと）を確かめる。

## 3. コミット前の確認手順

1. `git status`、`git diff --stat`、`git diff --cached --name-only` で、ステージが空であることを確かめる。
2. `python3 -I Tools/precommit/audit_commit_units.py` を実行する（読み取りのみ）。
   - すべての変更ファイルが、ちょうど1つのコミット単位か除外に入っていること。
   - Unity のアセットとその `.meta`（新しいフォルダの `.meta` を含む）が、同じ単位に入っていること。GUID の重複がないこと。
   - 個人情報・端末情報らしきものがないこと。新しいファイルは全行、変更したファイルは追加した行を調べる。
     - 一般的なパターン（ホームの絶対パス、メールアドレス、端末の UUID、アプリのデータ領域、秘密鍵）に加えて、ローカルの禁止語リスト（`../_device_backup/precommit_denylist.local.txt`）も使う。
     - 結果は行番号だけを出し、見つけた語そのものは表示しない。
   - 依存する単位（先にコミットする単位）が正しいこと。
   - AssetPipeline の素材は、`./assetpipe commit-plan <受付ID>` の結果と一致していること。
3. 単位ごとに、`git add -- <その単位のファイル>` でパスを明示してステージする。`git add -A` や `git add .` は使わない。
4. `git diff --cached --name-only` が、その単位のファイルだけであることを確かめる。
5. Unity のコンパイルとテスト（EditMode・PlayMode）を確かめてからコミットする。
6. AssetPipeline の素材を含む単位をコミットしたら、`./assetpipe register <受付ID>` で記録する。コミットは作られない。

## 4. AssetPipeline の素材と Unity の `.meta`

- 画像だけをコミットすると、`.meta`（GUID）や参照（`SkinCatalog.asset` など）と別々の、不完全なコミットになる。
- そのため、`config/assets.json` で `commit_with`（一緒にコミットするファイル）と `referenced_by`（GUID を参照するファイル）を書いた素材は、AssetPipeline が画像だけをコミットすることはない。
- 手順：
  1. `register --no-commit` で配置する。
  2. Unity で取り込み、`.meta` を作らせる。
  3. `commit-plan` で単位を確認する。
  4. 手で単位をまとめてコミットする。
  5. `register` で記録する。
- 単位の一部しかコミットされていない場合、`register` は登録済み（REGISTERED）にしない。
- ホーム素材（`commit_with` なし）は、今までどおり画像1枚のコミットで登録する。

## 5. 履歴に入ってしまった場合

- 履歴の書き換え（force push など）は、ユーザーの判断なしに行わない。見つけたら、すぐに報告する。
- 鍵・トークンが入った場合は、履歴の扱いとは別に、その鍵を無効にすることを最優先にする。
