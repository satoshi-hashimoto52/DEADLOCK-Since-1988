## 2. 試作型特殊SMG の設計案

### 2-1. 名称と識別子（案）

| 項目 | 案 | 備考 |
|---|---|---|
| 正式名称 | 第1案「SMG-88X プロトタイプ」、第2案「M88 試作短機関銃 "ナイトオウル"」、第3案「XSM-88 "ランタン"」 | 1988年の試作品という設定。ユーザーが選ぶ（未決定） |
| 武器ID | `proto_smg_x88` | 既存の `proto_*` の命名に合わせた案。保存データのキーになるので、決めたら変えない |
| ベース武器 | `proto_smg`（操作・ADS・リロードの方式は同じ） | 値は別のアセット。SMG のアセットを参照・継承する仕組みは作らない（SMG の値が変わっても EPIC が勝手に変わらないように） |
| カテゴリ | SMG | [WEAPON_EXPANSION](WEAPON_EXPANSION_STAGE30.md) 6章の `category` |
| レアリティID | `epic`（仮） | **レアリティの体系そのものが未決定**。下の5章の案で決める |

- EPIC の外観は**スキンでは作れない**（スキンは色替えだけ）。別の武器として、専用の画像を持つ。

### 2-2. 基本性能と固有特性（案）

方針：**SMG の完全上位互換にしない。** 性能差は、今ある欄（威力・発射間隔・装弾数・リロード・減衰・反動）だけで作る。新しい仕組み（固有パッシブ）は、仕様で将来構想（§7.3）なので今回は使わない。

| 項目 | SMG（案A、未承認） | 試作型特殊SMG（仮） | 差 |
|---|---:|---:|---|
| 威力 | 17 | 18 | ＋（倒すのに必要な命中は同じ6発） |
| RPM | 900 | 950 | ＋（倒すまで 0.33秒 → 0.32秒） |
| 装弾数 | 35 | 28 | **−**（1つの弾倉で倒せる人数が減る） |
| リロード | 1.6秒 | 1.9秒 | **−** |
| 距離減衰 | 25mから下がる（案A） | 20mから下がり、35mで0.6・60mで0.35 | **−**（遠距離は SMG より弱い） |
| 腰だめ拡散 | 1.0° | 1.1° | ほぼ同じ |
| ADS拡散 | 0.35° | 0.4° | **−** |
| 反動 | 上＋左右交互・弱 | 上＋左右交互・弱。横の角度を大きく（0.5°） | 縦は小さいが横に揺れる（扱いの癖） |
| ADS時間 | 0.15秒 | 0.16秒 | ほぼ同じ |

- 固有特性の言い方（案）：「試作の高速機構。近距離では SMG より速く倒せるが、弾倉が小さく、遠くでは当たっても弱い」。
- **SMG の値（案A）は未承認。** SMG の正式な値が決まったら、同じ差の付け方で EPIC の値を出し直す。
- 将来の固有パッシブ（例：撃破後の短い加速）は、Q-018 が決まってから別に設計する。

### 2-3. 専用外観と演出（1988年の試作品、過度なSFにしない）

## 3. ガチャとの連携に必要なデータ（設計案）

武器の性能（`WeaponDefinition`）と、ガチャ・所持品のデータを分ける（GAME_SPEC §13「武器定義、所持品、出撃中の状態、永続アカウント情報を分離」に合わせる）。

### 3-1. 目録（ScriptableObject、Git で管理する定義）

| データ（案） | 中身 |
|---|---|
| `ItemCatalog` | 入手できるもの全部の一覧。1件＝`itemId`（安定ID。例 `weapon.proto_smg_x88`）、`kind`（Weapon・Skin・Skill）、`refId`（武器なら `weaponId`、スキンなら `weaponId`＋`skinId`）、`rarity`、表示名、側面図など表示用の参照 |
| `RarityTable` | レアリティの一覧（ID・表示名・表示色・並び順）。**中身は未決定**。例として `common`・`rare`・`epic` を置く場合も、ユーザーの決定まで仮 |
| `GachaPool` | ガチャ1種類の定義：`poolId`、カテゴリ（スキン／武器／スキル、または混合）、消費（単発100・11連1,000、D-017）、排出の重み（アイテムかレアリティごと）、確定枠のルール、版 |
| 確定枠のルール | 「11枠のうち1枠」（D-017）だけを固定。その枠の中身（レアリティの下限・未所持の保証など）は**未決定**なので、ルールを差し替えられる形にする |

### 3-2. プレイヤーのデータ（保存）

| データ（案） | 中身 |
|---|---|
| ポイント残高 | 整数。増減はすべて記録（理由：試合の順位・ガチャ・開発用） |
| 所持品 | `itemId` → 入手日時・入手経路・重複回数 |
| ガチャ履歴 | 1回の引き＝日時・`poolId`・プールの版・各枠の結果・確定枠の位置・消費ポイント。保存する件数の上限は未決定 |
| ロードアウト | メイン銃の `weaponId`・近接・スキル・スキン。持っていない武器は選べない |
| 初期支給 | 最初から持つ武器（ライフル・SMG・ナイフ？）。**未決定**（GAME_SPEC §5「具体的な武器は未決定」） |

- 保存の方式：端末の設定（PlayerPrefs）とは別に、版付きのファイル（例：`persistentDataPath/account/profile_v1.json`）にする案。設定を消しても所持品が消えないように、分けて持つ。
- **本番のポイントと所有を端末の保存だけで管理するかは、仕様で「別途判断」**（GAME_SPEC §13、Q-024）。この保存は試作用とし、サーバー側の保存に移せる形（IDと版で表す）にする。
- 互換性：今の保存（スキンの選択など）は変えない。所持していないスキンを選んでいる保存データがある場合は、所持品の仕組みを入れたときに「標準」に戻すか、そのまま使えるようにするかを決める（未決定）。今のスキン `test_green`・`test_navy` はテスト用なので、目録に入れない案。

### 3-3. 処理の流れ（案）

1. ガチャを引く：残高の確認 → 消費 → 抽選（確定枠を含む）→ 所持品に追加（重複なら重複の処理）→ 履歴 → 保存。途中で失敗したら、消費と追加の両方を取り消す（1つの書き込みにまとめる）。
2. 装備：Gear → Loadout で所持している武器から選ぶ → 保存 → 試合前の準備（30秒）で切り替え。
3. 試合：ホストが、各プレイヤーの武器IDを定義に対応させる（オンラインの武器の同期は別の段階）。

### 3-4. テスト用の確定排出

- 開発ビルドとEditorだけで使える「乱数の種の指定」と「次の結果を指定する」機能（リリースビルドに入れない。今の開発用コードと同じ方法 `Deadlock.Dev`）。
- テストでは、本番の残高・所持品のファイルを使わず、一時フォルダを使う。

## 4. 所持・重複・装備条件

| 項目 | 案 | 状態 |
|---|---|---|
| 入手後の選択 | 入手すると、Gear → Loadout のメイン武器の選択肢に出る。EPIC だからといって自動で装備しない | 仮 |
| 装備の条件 | 所持していること（レアリティによる制限はない） | 仮 |
| 重複入手 | 武器は1つあれば足りる。重複したときの補填（ポイントの一部を返す、別の通貨など）は**未決定**（Q-022）。決まるまでは「重複回数を記録するだけ」 | 未決定 |
| 死亡・試合 | 失わない（D-007） | 確定 |
| 性能の公平さ | EPIC は SMG の上位互換にしない（2-2）。スキンは性能を変えない（D-008） | 方針（性能値は未承認） |

## 5. レアリティと排出確率（決めないこと）

- レアリティの数・名前・色、各レアリティの排出確率、確定枠の中身、天井、重複の補填は、**すべて未決定**（GAME_SPEC §4.2、Q-021・Q-022）。
- この文書では、データの形（`RarityTable`・`GachaPool`・確定枠のルール）だけを決め、値は空欄のままにする。
- ユーザーに決めてもらうこと：
  1. レアリティの段階（例：3段階か4段階か）と名前。「EPIC」をその1つとして使うか。
  2. 武器・スキン・スキルを同じガチャに混ぜるか、カテゴリ別か（GAME_SPEC §4.1 で暫定）。
  3. 各レアリティの排出確率（表示する確率）。
  4. 11連の確定枠の中身（例：一定以上のレアリティ、未所持の保証の有無）。
  5. 重複の扱い、天井の有無。
  6. 初期支給の武器と、試作型特殊SMG を最初のプールに入れるか。
  7. 本番のポイント・所有の保存場所（端末だけでよいか）。
